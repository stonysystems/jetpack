# Making m=101+raft truly fp100 — 2026-05-06

Goal (set 2026-05-06 by user): the "Raft + JetPack adaptive" mode (`-m 101`) should match `-m 100` (always-attempt) in steady-state peak throughput. Until this work, m=101 was leaving ~13 % of peak tput on the table at c=200 and effectively becoming m=0 (vanilla Raft) under saturation.

## Final result

`rule_raft -m 101` (after fix), six-cell sweep, 60c1s5r10p, rw_1000000, YCSB_A:

| conc | tput (req/s) | p50 (ms) | fp%-attempted (s0..4) | vs `rule_raft -m 100` |
|---:|---:|---:|---:|---|
| 1   | 39.9    | 161  | 96.6 % | match |
| 50  | 2 962   | 161  | 99.3 % | match |
| 100 | 5 958   | 163  | 99.9 % | match |
| 150 | 8 941   | 165  | 99.7 % | match |
| **200** | **11 689** | 518  | 94.6 % | **+1 %** (within noise; m=100=11 578) |
| 300 | 9 341   | 1 116 | 100 % | **+36 %** (m=100=6 854 with 7/10 partial fail; m=101 stayed 10/10) |

The tput-vs-conc curves on `tput_lat_raft.png` and the headline `tput_ave_grid_6protocols.*` figure now show m=101 cleanly tracking m=100.

## Codebase changes

All in [`src/deptran/rule/coordinator.cc`](../src/deptran/rule/coordinator.cc), ordered by commit:

1. **`7c1a8f97` — drop 500 ms cap in m=101's adaptive gate (b)**.  Replaced
   `cli2cli_[6+w].recent_100_ave() < std::min(cli2cli_[8+w].recent_100_ave(), 500.0)`
   with a pure-relative comparison `< cli2cli_[8+w].recent_100_ave()`. The 500 ms
   ceiling was forcing the bandit to take over once cluster latency rose
   above 500 ms (which it does at saturation), independent of whether
   fast-path was actually beating slow-path. *Net effect on its own:
   none — see below.*
2. **`99b6a734` — m=101+raft hardcode `go_to_fastpath_=true` AND
   line-249 bandit gate**.  Two coupled changes:
   - Hardcode the m=101+raft branch to `go_to_fastpath_=true`. The
     adaptive gate had self-locked at saturation in v2 data (see
     diagnosis below); forcing true makes the gate-level decision
     identical to m=100.
   - Gate the bandit feedback site at line 249 on `go_to_fastpath_`:
     ```cpp
     if (go_to_fastpath_) {
       client_worker_->one_armed_bandit_.Record(fast_path_success_);
     }
     ```
     This was the death-spiral root cause for the original m=101 (see
     diagnosis below). Defends against future m∈[1,100] adaptive
     variants from the same trap.
3. **`7e74a713` — disable the m=101+raft CPU-throttle (lines 137-179
   formerly)**.  This was the load-bearing bug. There was a CPU-based
   ramp that ran AFTER the gate decision and probabilistically reset
   `go_to_fastpath_=false` when leader CPU exceeded 70 % (linear ramp
   to 100 % off at 95 % CPU). At c=100 with leader at 99 % CPU, this
   was ~100 % override probability — making the line-95 hardcode a
   no-op. Disabled per user request to make m=101+raft truly fp100.
   The block is preserved as comments for easy reversal.

## The diagnostic journey (why three commits)

The user's request was simple ("make m=101 do fp100"). The three-commit path was forced by hidden interactions:

### Symptom

At the start of 2026-05-06, `rule_raft -m 101` data showed:
- c=50: latency 161 ms ✓ (clean fast path)
- c=100: latency **394 ms** ✗ (looks like slow path)
- c≥150: latency 1700-1900 ms ✗ (deep slow-path)
- c=200 tput: 10 084 r/s vs m=100's 11 577 r/s (13 % gap)

### Hypothesis 1: 500 ms cap in adaptive gate

Suspected the `< std::min(slow_path_lat, 500.0)` clause was clipping the latency-relative comparison once cluster latency exceeded 500 ms. Dropped the cap.

**Effect**: none. c=200 tput went 10 084 → 9 779 (within noise). Hypothesis disproved.

### Hypothesis 2: bandit death spiral via line-249 fake-fail signals

Inspected the .res files for fast-path attempt counts:

| conc | fast-path attempts | original-path | fp% |
|---:|---:|---:|---:|
| 50 | 2 993 | 90 | 97.1 % ✓ |
| **100** | **53** | 5 888 | **0.9 %** ✗ |
| 150 | 0 | 8 961 | 0 % |

Sharp transition between c=50 and c=100. Found the cause at [coordinator.cc:249](../src/deptran/rule/coordinator.cc#L249):

```cpp
client_worker_->one_armed_bandit_.Record(fast_path_success_);
```

Fired for **every** transaction, including ones where `go_to_fastpath_=false` (no spec broadcast → `fast_path_success_` stayed at its initialiser=false). The bandit got fed fake "fail" signals on un-attempted transactions, dropping its `success_cnt/attempt_cnt` ratio, making `ConsultAttempt()` vote no, locking the gate closed for the rest of the run.

Self-fulfilling-prophecy death spiral. Triggered at c=100 because that's where leader CPU first crossed the threshold for transient `(b)` flips during warmup.

**Fix**: gate the Record on `go_to_fastpath_`. Combined with hardcoding `go_to_fastpath_=true` for m=101+raft (which the user explicitly requested).

**Effect after fix #2**: c=100 fp% climbed but to *only ~1.5 %* on remote client hosts (server5..9), and **0 %** on raft-replica-collocated client hosts (server0..4). Worse than before in some cases. Hypothesis incomplete.

### Hypothesis 3 (the actual cause): CPU-throttle override

Added a debug Log_info inside the m=101+raft branch:
```
[FP100_HARDCODE_HIT] m=101+raft hardcode branch entered tid=... rate=101 replica_proto=0x400
```

Confirmed: the hardcode fires on every coordinator coro on every host. `replica_proto_=0x400` (=MODE_RAFT). `go_to_fastpath_=true` IS being set.

But fp% was still 0 on server0..4. Theoretical equivalence to m=100 was provably broken by something downstream. The user spotted the culprit at lines 137-179 (in [`src/deptran/rule/coordinator.cc`](../src/deptran/rule/coordinator.cc#L137) before the fix):

```cpp
} else if (replica_proto_ == MODE_RAFT || replica_proto_ == MODE_FPGA_RAFT) {
    // Adaptive throttle: at high leader CPU the fast-path spec RPCs
    // become pure overhead on the pinned leader core...
    constexpr double FP_LO = 70.0;
    constexpr double FP_HI = 95.0;
    ...
    bool cpu_disabled = (avg_leaders - FP_LO) > rand_val;
    if (cpu_disabled) {
      go_to_fastpath_ = false;   // overrides the line-95 hardcode!
    }
```

This block ran AFTER the gate decision and reset `go_to_fastpath_=false` whenever leader CPU exceeded ~70 %. At c=100 with leader at 99 % CPU, override probability was ~100 % — fully neutering the hardcode.

**Why it existed**: a deliberate graceful-degradation feature. At high leader CPU, sending spec-broadcast RPCs steals cycles from the Raft replication loop, which can drop overall tput below vanilla Raft. The throttle was supposed to make jp-raft-adaptive degrade gracefully to vanilla at peak load.

**Why it stayed silent for so long**: m=100 (the always-attempt mode) doesn't enter this `else if` branch — it's nested inside `if (rate == 101)`. So m=100 always sees fp%=99 even at saturation, while m=101 always sees fp% drop hard at saturation. Both behaviors were "by design", just different defaults.

**Fix**: comment out the block when m=101+raft. User chose to disable it entirely (line-by-line comments preserved for easy reversal).

## Z(b) closure

This work also closes Z(b) ("CURP and rule_raft@m101 should differ in only attempt-rate"). With the throttle disabled, `none_curp@200` and `rule_raft@m101` now match within run-to-run noise across the whole conc range, including saturation. The thesis "attempt-rate is the only delta" is now empirically confirmed at the gate level (Z(a) audit, 2026-05-06) AND at the runtime level (this work).

## Reversal

If we ever want to restore the graceful-degradation property:

1. Uncomment lines 137-179 (currently a 30-line block of `//` comments).
2. Optionally also revert the line-95 hardcode to the adaptive gate.
3. Keep the line-249 bandit gate fix — it's a defensible correctness change regardless.

# Max-Throughput Experiment Setting (canonical)

This is the **canonical spec** for the max-throughput sweep. All runs that
follow this setting should produce directly comparable numbers. If a run
deviates, note the deviation in that run's own results folder.

Applies to the 5 scalable protocols (Raft, SwiftPaxos, EPaxos,
Jetpack+Raft fp100, Jetpack+Raft adaptive) and the three baselines
(naive_rpc, naive_fastpath, naive_raft).

## Cluster

- 5-node `zoo` testbed — `.101`–`.105` = `zoo1`–`zoo5` (1-indexed display
  name; internal `locale_id` is still `0..4`).
- Each `deptran_server` pins its reactor thread, disk-poll thread, **and**
  main server thread to **core 17**. Driven by `SERVER_CORE_ID=17`
  (parsed in [s_main.cc](../src/deptran/s_main.cc); replaces the hardcoded
  core-1 pin). The mid-10 s `/proc/stat` CPU sampling uses the same core.
- For protocols with a fixed leader/master/unique server role, that role
  is placed at `zoo2` (locale_id=1, IP `.102`). Routing is handled in
  [communicator.cc `GetLeaderForPartition`](../src/deptran/communicator.cc)
  for `naive_rpc` / `naive_raft`; other protocols already route there by
  default.
- Clients are **uniformly distributed** across `zoo1`…`zoo5` (round-robin).
  The generator [scripts/gen_client_config.sh](../scripts/gen_client_config.sh)
  produces `Nc1s5r5p-zoo.yml` on demand. Exception: the **N=1 baseline**
  places its single client on `zoo2` (co-located with the leader) so the
  stop criterion — which is measured at zoo2 — has a meaningful baseline.

## Workload

- `rw_1000000.yml` (R/W key space = 1 M keys, uniform).
- `client_open.yml` (open-loop client).
- `concurrent=500` per client (`concurrent_500.yml`).
- `WAN_DELAY_MS=20` → 40 ms injected RTT.
  - **Caveat**: the current `_wan_wait()` delays every RPC unconditionally;
    colocated client↔leader hops pay the fake 40 ms RTT even though they
    physically don't cross hosts. This inflates 1-client baselines by
    ~40 ms. Listed as "optional WAN-aware WAN_WAIT" in the TODO.
- **Duration**: 30 s per data point.

## Metrics

All metrics come from the **mid-10 s window** (experiment seconds 10–19).

- **Throughput** (`cmd/s`): `Mid throughput is …` line emitted by
  [s_main.cc](../src/deptran/s_main.cc). The cli2cli machinery already
  restricts counts to the mid-10 s window.
- **Latency** (`p50`, `p90`, `p99` in ms): per host, from the
  `All-efficient-attempts statistics` log line. Also mid-10 s only.
- **CPU**: per host, the **mean** of ~10 per-second core-`SERVER_CORE_ID`
  `/proc/stat` samples over the mid-10 s window. Emitted as
  `server average : X.XXX` (alongside the legacy `server median` line)
  by [s_main.cc](../src/deptran/s_main.cc). **Headline** number is the
  avg across the 5 hosts' averages, **not** the max across hosts.

## Sweep

- Client counts: start with **N=1, 50, 100**, then adaptively bisect /
  extend until the saturation point is within ±5 clients.
- **Saturation criterion**: `zoo2 p50 latency > 2 × (1-client baseline)`.
  - Historical 1-client baselines (reference only — actual baseline is
    measured per run at N=1): ~85 ms Raft, ~42 ms others.
- Driven by [scripts/run_adaptive_sweep.sh](../scripts/run_adaptive_sweep.sh).

## Presentation

**One table per protocol**. Rows = every N attempted (including bisection
steps, not just the converged saturation point). Columns:

| N | tput | zoo2 p50 | zoo2 p90 | zoo2 p99 | zoo3 p50 | zoo3 p90 | zoo3 p99 | zoo1 cpu | zoo2 cpu | zoo3 cpu | zoo4 cpu | zoo5 cpu | avg cpu |

The CSV written to `<results_dir>/<label>-adaptive.csv` matches this
column layout with an extra `note` column (`baseline` / `ok` / `stop` /
`bisect-ok` / `bisect-stop`).

## Per-run artifacts

Every run must write the following into `results/<date>-<experiment_name>/`:

- `<label>-adaptive.csv` — the wide results CSV (above).
- `<label>-N<n>c500-zooK.res` — per-host raw stdout from `deptran_server`
  (contains `Mid throughput`, `server median`, `server average`, and the
  `*-attempts statistics` latency lines).
- `<label>-N<n>c500-zooK-cpustat.txt` — per-host 1 s `/proc/stat` samples
  during the run, from [scripts/run_single_exp.sh](../scripts/run_single_exp.sh).
- `<label>-N<n>c500.runlog` — the orchestration script's own stdout for
  that data point.
- `SETTING.md` — a snapshot of this setting and the exact env vars /
  protocol cfg used, auto-generated by `run_adaptive_sweep.sh` at start
  (so the folder is self-contained and interpretable without this doc).

## How to run

```bash
# Single protocol, core-17 pin:
SERVER_CORE_ID=17 scripts/run_adaptive_sweep.sh \
    naive_raft none_naive_raft.yml 0 \
    results/2026-04-20-naive-raft-core17

# Other protocols, same setting:
SERVER_CORE_ID=17 scripts/run_adaptive_sweep.sh raft       none_raft.yml             0 results/<date>-raft-core17
SERVER_CORE_ID=17 scripts/run_adaptive_sweep.sh swiftpaxos none_swiftpaxos.yml       0 results/<date>-swiftpaxos-core17
SERVER_CORE_ID=17 scripts/run_adaptive_sweep.sh epaxos     none_epaxos_corrected.yml 0 results/<date>-epaxos-core17
SERVER_CORE_ID=17 scripts/run_adaptive_sweep.sh jp-raft-fp100    rule_raft.yml 100 results/<date>-jp-raft-fp100-core17
SERVER_CORE_ID=17 scripts/run_adaptive_sweep.sh jp-raft-adaptive rule_raft.yml 101 results/<date>-jp-raft-adaptive-core17
```
